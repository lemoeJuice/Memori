# Memory Journal 设计文档

## 1. 产品定位

这是一个轻量的私人生活记录应用。

它不要求用户每天写完整的文字日记，而是允许通过 **时间、位置、照片与可选文字** 留下生活痕迹。即使没有文字，也可以只依靠照片与位置完成一次记录。

核心目标不是“总结每天发生了什么”，而是：

> 低负担地留下当下，之后可以沿着时间重新翻回去。

产品整体应避免传统日记应用的“任务感”“表单感”和“情绪管理工具感”，更接近一个私人记忆墙。

---

## 2. 核心设计原则

### 2.1 记录成本尽可能低

一条记录至少可以只有：

- 时间
- 位置

也可以包含：

- 一张照片
- 自定义地点描述
- 一小段文字

所有文字字段都应可留空。

### 2.2 首页不是编辑器，而是记忆墙

首页首先是一个可持续向上翻阅的时间流，而不是“今天要写什么”的输入页面。

新记录入口直接作为时间流的一部分存在。

### 2.3 新的记录在下方

时间顺序为：

- 旧记录在上
- 新记录在下

首次进入首页时默认滚动到底部，直接看到最近记录与新的记录入口。

### 2.4 同一次应用生命周期保留浏览位置

用户从其他页面切回首页时，应恢复本次应用生命周期内最后一次浏览位置，而不是重新跳到底部。

重新启动应用后，再默认进入最新位置。

### 2.5 尽量不使用弹窗

常见操作尽量以内联展开、卡片扩展、局部状态变化完成。

避免使用大量 Modal 或新页面打断时间流。

---

## 3. 整体信息架构

当前版本包含三块主要结构：

1. **Memory Wall / 首页**
   - 瀑布流记忆墙
   - 新记录入口
   - 时间分隔
   - 卡片展开操作
   - 回忆卡片导出

2. **Memory Map / 地图**
   - 地图展示记忆点
   - 时间滑动 / 时间范围筛选
   - 地点聚合与记忆回看
   - 顶部搜索入口
   - 后续可扩展轨迹显示

3. **Settings / 设置**
   - 外观
   - 定位与照片行为
   - 图片存储
   - 数据导出
   - 隐私与显示选项

---

# 4. 首页：Memory Wall

## 4.1 基础布局

首页使用 **瀑布流 / Masonry Layout**。

不同记录卡片可以根据内容呈现不同高度：

- 只有位置 / 少量文字：小卡
- 普通照片记录：中卡
- 信息较多的照片记录：较高卡

不强制所有卡片统一尺寸，避免过强的数据库列表感。

整体视觉更接近“私人记忆墙”。

---

## 4.2 时间方向

首页时间顺序固定为：

```text
更早
↑
│
│  历史记录
│
│  最近记录
│
↓
现在
```

新的内容始终出现在底部。

首次进入首页：

- 默认定位到最底部
- 展示最近记录
- 最下方展示新的记录入口

本次应用生命周期内：

- 记住用户当前滚动位置
- 切换页面再回来时恢复原位置

---

## 4.3 新记录入口

新的记录入口本身就是一个空白卡片容器。

视觉上与普通卡片保持同一套设计语言，但内容是一个明显但轻量的 `+`。

示意：

```text
╭──────────────╮
│              │
│      ＋      │
│              │
╰──────────────╯
```

它永远出现在当前时间流的最底部。

点击后不跳转新页面，而是 **在原位置展开为编辑卡片**。

编辑完成并保存后：

1. 当前编辑卡变成正式记录卡片
2. 新的 `+` 卡片自动出现在它下方

形成一种持续生长的时间流。

---

## 4.4 新记录编辑状态

编辑卡尽量保持极简，不做传统表单。

包含：

- 当前时间
- 照片区域
- 定位状态
- 自定义地点描述
- 可选文字
- 保存

示意：

```text
18:42 · 10 月 4 日

[ 添加照片 ]

📍 已记录当前位置
地点描述……

写点什么……
（可选）

      保存
```

### 照片与定位规则

#### 有照片时

优先尝试读取照片 EXIF GPS。

优先级：

1. 照片 EXIF GPS
2. 当前设备定位
3. 无位置

#### 没有照片时

直接使用当前设备定位。

如果用户拒绝定位权限，则允许无位置保存。

### 地点描述

地点描述始终由用户自己填写，完全可空。

示例：

- 每天去的奶茶店
- 公交上
- 学校旁边
- 随便坐到这里了

机器坐标与用户地点描述是两个不同字段。

坐标主要服务于未来地图与空间检索；地点描述服务于人的记忆。

---

# 5. 时间分隔设计

## 5.1 分隔结构

时间流中可以在不同时间段之间插入分隔线。

推荐两级：

- 月级分隔：强视觉
- 日级分隔：弱视觉

初期可优先实现月级分隔。

---

## 5.2 月份标记

月份分隔线左侧悬挂一个较大的日期标记，例如：

```text
26/09 ─────────────────────
```

其中：

- `26` 表示年份
- `09` 表示月份

该标记是时间流中最强的时间视觉锚点之一。

可以考虑在滚动经过某个月份时短暂 Sticky，但不应长期占据大量空间。

---

## 5.3 日期视觉层级

建议视觉优先级：

1. 月份标记
2. 记录卡片中的照片 / 内容
3. 单条记录时间
4. 日级分隔

避免日期元素过多导致页面变成时间表。

---

# 6. 卡片设计

## 6.1 视觉风格

整体可以参考 Moneko 的：

- 浅蓝 / 蓝白色系
- 柔和圆角
- 低饱和度
- 留白
- 轻量阴影

但本项目应进一步弱化“工具感”。

首页更接近相册 / 记忆墙。

---

## 6.2 玻璃拟态

记录容器采用轻量玻璃拟态：

- 半透明背景
- 轻微背景模糊
- 极弱边框
- 很轻的阴影

不要做重玻璃效果。

目标是：

- 卡片与背景图融合
- 保持可读性
- 不抢照片主体

---

## 6.3 背景图

首页支持设置自定义背景图片。

背景图应被视为整个记忆墙的一部分，而不是卡片内容。

建议支持：

- 用户自定义背景
- 轻微暗化 / 模糊选项
- 卡片玻璃强度调节

后续可以考虑按月份切换背景，但第一版无需实现。

---

## 6.4 卡片内容优先级

有照片时：

**照片 > 地点描述 > 时间 > 正文**

无照片时：

**地点描述 / 正文 > 时间 > 机器位置**

精确坐标默认不应出现在主卡片中。

---

# 7. 卡片展开操作

## 7.1 基础交互

点击普通记录卡片后，不弹出 Modal，也不跳新页面。

卡片向下扩展，露出一排操作按钮。

示意：

```text
╭────────────────╮
│    原卡片内容    │
├────────────────┤
│ 编辑  分享  收藏  删除 │
╰────────────────╯
```

操作区属于卡片自身的一部分。

---

## 7.2 展开状态

原则：

- 同时允许存在展开状态
- 但默认点击新卡片时自动收起上一张已展开卡片

这样可以避免整个瀑布流被多个菜单撑乱。

---

# 8. 分享回忆卡片

## 8.1 入口

分享功能不作为首页主按钮出现。

只有用户点击某条记录并展开卡片菜单后，才显示：

**导出回忆卡片**

这是一个低频操作。

---

## 8.2 导出方式

点击后不打开新页面。

直接在当前卡片下方继续展开一个分享预览区域。

可以配置：

- 是否显示地点描述
- 是否显示日期
- 是否显示正文
- 是否使用原照片背景
- 是否使用应用主题背景
- 输出比例

推荐比例：

- 1:1
- 4:5
- 9:16

最后生成一张可保存 / 分享的图片。

---

## 8.3 分享卡片视觉

导出内容应保持应用本身的视觉语言：

- 圆角
- 轻玻璃效果
- 日期标记
- 照片优先
- 少量文字

但生成结果不应包含应用导航、按钮等 UI。

---

# 9. 第二屏：Memory Map

地图页是应用的第二个核心视角。

它与首页的关系不是“功能页”和“主页面”的关系，而是同一批记忆数据的两种浏览方式：

- Memory Wall 从时间方向浏览
- Memory Map 从空间方向浏览

当前阶段只定义产品结构和交互，不在本设计文档中绑定具体地图提供商、SDK、瓦片源或轨迹实现方案。

## 9.1 地图主体

地图占据页面主体区域。

地图上展示当前时间范围内存在位置数据的记忆记录。

基本行为：

- 单条记录显示为记忆点
- 邻近记录可以聚合为地点簇
- 点击记忆点可以查看对应记录
- 点击地点簇可以浏览该地点附近或同一地点的多条记忆

地图视觉应尽量保持克制，让照片、记忆点和时间变化成为重点。

---

## 9.2 时间滑动视角

地图页需要提供沿时间浏览记忆的能力。

基础形态可以是位于地图下方的时间滑动控件。

支持两种模式：

1. **时间点模式**
   - 拖动到某一天 / 某一时间段
   - 地图展示该时刻附近的记忆

2. **时间范围模式**
   - 选择一段时间范围
   - 地图展示这段时间内的所有相关记忆

拖动时间时，地图中的记忆点应平滑出现、消失或聚合，避免明显跳变。

后续加入轨迹功能后，同一时间控件继续用于控制轨迹显示范围。

---

## 9.3 地点聚合与回看

如果同一个地点存在多次记录，不应只展示最近一条。

点击地点后可以看到该地点累计留下的记忆，例如：

```text
这里有 12 条记忆

[照片] 10/04  每天去的奶茶店
[照片] 09/28  今天坐了很远
       09/21  没写什么
```

这样可以让经常出现的地点随着时间逐渐形成“记忆重量”。

---

## 9.4 搜索入口

搜索入口位于地图页上方。

### 默认状态

平时只显示一个圆形搜索 Icon，尽量减少对地图视野的占用。

```text
  🔍
```

### 展开状态

点击后横向展开成类似浏览器地址栏 / 搜索框的长条胶囊：

```text
🔍  搜索地点、文字、日期……
```

特点：

- 圆角胶囊
- 横向展开动画
- 不跳转到独立搜索页
- 搜索直接作用于当前地图视角
- 可用于搜索地点描述、正文、日期等记录信息

具体搜索结果的地图呈现方式可以在地图实现阶段继续细化。

---

## 9.5 轨迹扩展

第一版不要求持续记录轨迹。

地图页需要在结构上预留后续加入轨迹的能力：

- 按时间范围显示轨迹
- 轨迹与记忆点共同出现
- 记录点可以作为轨迹中的显式记忆节点

轨迹属于后续增强功能，不应影响第一版以“事件点记录”为核心的低负担体验。

---

# 10. 设置页

设置页保持简单。

## 10.1 外观

- 背景图片
- 背景模糊 / 暗化程度
- 卡片玻璃透明度
- 卡片模糊强度
- 圆角大小
- 主题模式

---

## 10.2 照片

- 图片压缩质量
- 是否保留原图
- 默认最大分辨率
- 是否读取 EXIF 元数据

---

## 10.3 定位

- 是否允许记录位置
- 有照片时是否优先使用 EXIF GPS
- EXIF 无 GPS 时是否使用当前位置
- 是否显示精确坐标

默认推荐：

- 开启位置记录
- EXIF 优先
- 无 EXIF 时使用当前位置
- UI 中隐藏精确坐标

---

## 10.4 数据

- 导出全部记录
- 数据备份
- 数据恢复
- 清理缓存
- 存储占用查看

第一版建议至少支持：

- JSON 导出
- 图片文件一起打包导出

---

# 11. 性能设计

首页会长期累积大量记录，因此必须提前处理长列表性能问题。

## 11.1 不一次性渲染完整历史

不要将所有历史卡片同时挂在 DOM 中。

采用：

- 虚拟列表
- 分段加载
- 或两者结合

---

## 11.2 向上加载历史

当用户向上滚动接近当前已加载记录顶部时，再加载更早的一段。

关键要求：

**加载完成后当前屏幕内容不能跳动。**

推荐使用锚点补偿：

1. 记录加载前顶部可见卡片及其屏幕位置
2. 在上方插入旧记录
3. DOM 更新后重新计算该锚点的位置
4. 补偿 scroll offset

用户视觉上应感觉旧内容只是自然出现在上方。

---

## 11.3 图片加载

需要避免大量原图同时解码。

建议：

- 生成缩略图
- 首页优先展示缩略图
- 原图按需读取
- 使用懒加载
- 卡片离开较远视口时允许释放图片资源

---

## 11.4 滚动位置恢复

需要保存：

- 当前列表加载范围
- 当前滚动位置或可见锚点

同一次应用生命周期内切换 Tab 时直接恢复。

不要每次回首页都重新从底部开始。

---

# 12. 数据模型建议

一条记录至少可以包含：

```ts
interface MemoryEntry {
  id: string

  createdAt: number
  updatedAt: number

  photo?: {
    id: string
    thumbnail?: string
    original?: string
    exifTakenAt?: number
  }

  location?: {
    latitude: number
    longitude: number
    source: 'exif' | 'current'
    accuracy?: number
  }

  placeLabel?: string
  text?: string

  favorite?: boolean
}
```

注意：

- `location` 与 `placeLabel` 分开
- `text` 可空
- `photo` 可空
- 一条记录可以只由时间 + 位置构成

# 14. 地图范围说明

Memory Map 是当前应用三屏结构中的正式组成部分。

地图页的具体产品设计、时间轴、点位聚合、高德地图接入与配置方式统一见独立文档：

`memory-map-design.md`

主文档不重复维护地图实现细节，避免两份文档出现分叉。

当前版本仍暂不实现：

- 持续后台轨迹记录
- 自动生成地点名称
- 自动识别常去地点
- 导航 / 路线规划
- 云同步

# 14.1 首页实现约束

以下几点需要在实现前固定，避免瀑布流、时间顺序和虚拟化互相冲突。

## 月份作为一级分组

首页不要把“月份分隔线”和所有卡片一起交给一个全局 Masonry 算法。

推荐结构：

```text
MonthGroup
├── 26/08 ─────────────
│   └── 该月记录的 Masonry
├── 26/09 ─────────────
│   └── 该月记录的 Masonry
└── 26/10 ─────────────
    └── 该月记录的 Masonry + 新记录卡
```

这样月份分隔线始终完整跨越内容区域，也方便向上按月或分页加载。

## 保证视觉阅读顺序

记录的数据顺序必须始终是：

```text
旧 → 新
```

瀑布流不能使用会把 DOM 顺序变成“先填满第一列，再填第二列”的实现。

视觉阅读顺序应尽量保持从左到右、从上到下仍然对应时间递增。

实现可以自行选择 Masonry 库或布局算法，但不能为了视觉瀑布效果破坏时间顺序。

## 虚拟化优先保证稳定滚动

如果完整 Masonry 与通用虚拟列表难以同时稳定实现，优先保证：

1. 向上加载不卡顿；
2. 插入历史记录时视口不跳；
3. 返回首页后能恢复位置；
4. 图片懒加载与缩略图正常工作。

第一版不要求追求极端像素级 Masonry；允许使用近似瀑布布局换取稳定性。

## 新记录定位

新的 `+` 卡永远位于当前最新月份分组的最末尾。

保存后：

1. 编辑中的 `+` 卡原地变成正式记录；
2. 新的 `+` 卡追加在其后；
3. 不重新构建整个列表；
4. 不主动改变用户当前滚动位置，除非用户本来就在底部附近。

---

# 14.2 图片与本地存储约束

照片不要以 Base64 长字符串直接塞进记录对象。

建议：

- 元数据与记录存 IndexedDB；
- 图片使用 `Blob` / `File` 或独立图片表保存；
- 为首页和地图 Marker 单独生成缩略图；
- 原图是否保留由设置决定。

记录只保存图片 ID / 引用。

导出格式需要带版本号，例如：

```ts
{
  schemaVersion: 1,
  exportedAt: number,
  entries: [...]
}
```

以后数据结构变化时才能安全迁移和恢复。

删除记录时，需要同时清理不再被引用的图片 Blob / 缩略图，避免 IndexedDB 长期积累孤儿文件。

---

# 14.3 定位失败状态

定位是可选增强信息，不能阻止记录本身保存。

至少处理：

- 用户拒绝权限
- 定位超时
- 浏览器不支持
- EXIF 不含 GPS
- EXIF 解析失败

编辑卡中只需要给出轻量状态，例如：

```text
📍 已记录位置
📍 正在定位…
○ 未记录位置
```

失败后允许直接保存，不弹出阻断式错误窗口。


# 15. 整体体验目标

整个应用应该给人的感觉是：

- 安静
- 熟悉
- 很少要求用户做决定
- 不催促记录
- 不强调连续打卡
- 不把生活变成统计数据

首页的核心体验可以概括为：

> 往上翻，是已经发生过的生活；往下回到现在，最底部永远留着一个空位，等下一段记忆出现。
